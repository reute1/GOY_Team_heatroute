## 1. Задача в двух словах

Кейс ДИТ Москвы «Лидеры цифровой трансформации 2026». Новые здания (ОКС) нужно подключить к существующей теплосети. Сервис получает карту в GeoJSON и сам строит варианты новой сети труб с ценой.

**На входе** один файл GeoJSON (WGS 84):

| Объект | `object_type` | Что это |
|---|---|---|
| Источник тепла | `source` | точка, одна на набор |
| Существующая теплосеть | `heat_network` | линии с диаметром `diameter` |
| Существующие камеры | `heat_chamber` | точки, где соединяются трубы |
| Точки подключения зданий | `oks_connection_point` | точки с расходом `flow_tph`, т/ч |
| Ограничения | `restriction` | здания (`oks`), вода, ж/д, парки, дороги, газопроводы, кабели и т.д. |

**На выходе** — до трёх вариантов новой сети в одном GeoJSON: участки труб с расходом, диаметром, длиной, способом прокладки и ценой, новые камеры, технические узлы и сводка по каждому варианту.

**Главные правила** (из технического приложения):

- Трасса — прямые отрезки, поворот не больше 90°, без зигзагов.
- Ветвления только в камерах, к камере примыкает не больше 4 труб.
- Колец нет: от места врезки до каждого здания ровно один путь. Новые трубы не пересекаются между собой.
- Здания, вода, ж/д, парки обходятся с отступом (от зданий 5/7/9 м в зависимости от диаметра).
- Дороги, трамвай, газопровод, кабель, чужая теплосеть пересекаются **спецпроходом**: прямой участок, для дорог под углом не меньше 45°, цена × Kспец (1,05–1,75).
- Врезка: если в пределах 10 м от места врезки есть существующая камера со свободным местом — только в неё (5 млн ₽). Иначе строится новая камера (3/5/8/12 млн ₽ по наибольшему диаметру примыкающих труб, включая существующую).
- Диаметр — минимальный по расходу. У каждого диаметра есть предельная длина непрерывной серии участков; если превышена — берётся следующий диаметр. К месту врезки диаметр не уменьшается.
- Неподключённое здание — штраф `100 млн + 0,5 млн × расход`. Не подключать специально, чтобы было дешевле, нельзя.
- Сравнение вариантов: **S = 0,7 · C / 25 млн + 0,3 · L / 100** (C — стоимость, L — длина новой сети в метрах). Меньше — лучше.

**Технические требования:** Java 11, Spring Boot 2.6.3, PostgreSQL, springdoc-openapi-ui 1.7.0 (Swagger), docker-compose 1.29.2 на Ubuntu Server 22, загрузка файлов до 3 ГБ с потоковой обработкой, до 50 пользователей, 16 ГБ ОЗУ.

**Важно:** проверять будут на **других данных**, не на конкурсном наборе. Ничего под конкурсный файл подгонять нельзя, и мы этого не делаем.

Исходные документы: «2. ДИТ.pdf» (описание кейса), «Техническое приложение ЛЦТ.docx» (формальные правила) и «Разъяснения по вопросам ЛЦТ.docx». При расхождении действует техническое приложение (так сказано в разъяснениях, вопрос 16).

## 2. Что умеет сервис

- Загрузка GeoJSON до 3 ГБ через веб-интерфейс или REST API, асинхронный расчёт, статус задачи, выгрузка результата.
- Автоматический выбор мест врезки (в существующую камеру или новой камерой на трубе).
- Совместное подключение зданий с ветвлениями в камерах (дерево Штейнера).
- Обход запрещённых объектов с отступами, спецпроходы через дороги, трамвай, газопровод, кабель и существующую теплосеть, с техническими узлами на границах.
- Расчёт расходов, подбор диаметров с учётом предельной длины и невозрастания к месту врезки.
- Три содержательно разных варианта с ранжированием по S.
- Самопроверка каждого варианта (отступы с фактическими диаметрами, углы, предельная длина) — результат в сводке.
- Диагностика входных данных: пропущенные атрибуты, неизвестные типы ограничений, камеры не на сети и т.п. Некорректные объекты не роняют расчёт.
- Частичный результат, если какое-то здание подключить не удалось: список таких зданий и причина.
- Веб-интерфейс с картой (Leaflet + OpenStreetMap), Swagger UI, автономная HTML-карта результатов без сервера.
- Независимый валидатор на Python, который проверяет результат по правилам, не используя код сервиса.

## 4. Архитектура

```
 Браузер (index.html, Leaflet)            curl / Swagger UI
            │                                     │
            └──────────────┬──────────────────────┘
                           ▼
            JobController  (REST /api/jobs)            ← Spring Boot 2.6.3
                           │
            JobService: сохраняет файл на диск, ставит задачу
                        в пул потоков, статус и сводка → PostgreSQL
                           │
                           ▼
            HeatRouteEngine  (ядро, чистый JDK, без Spring)
              ├─ InputReader   потоковый разбор GeoJSON, WGS 84 → UTM 37N,
              │                двухпроходное чтение с областью поиска
              ├─ Planner       весь алгоритм: граф, поиск, варианты, ДУ, проверки
              │    ├─ Env       модель ограничений, проверка отрезка трассы
              │    ├─ VisGraph  граф видимости
              │    └─ SegGrid   пространственный индекс отрезков
              └─ OutputWriter  запись результата в GeoJSON (WGS 84)
```

Два уровня:

- **Ядро** (`ru.lct.heatroute.core`) написано на чистом Java 11 без внешних библиотек: свой потоковый JSON-парсер, своя проекция WGS 84 → UTM 37N (EPSG:32637), своя вычислительная геометрия. Его можно запустить из командной строки без Spring и без базы. Расчёт детерминирован: одинаковые данные дают одинаковый результат.
- **Сервис** (`ru.lct.heatroute.api`, `ru.lct.heatroute.service`) — тонкая обёртка на Spring Boot: приём файла, очередь задач, хранение статусов в PostgreSQL, выдача результатов, Swagger.

Файлы хранятся на диске (`STORAGE_DIR`, в Docker — том `jobs`): `<id>/input.geojson` и `<id>/result.geojson`. В базе — таблица `jobs` (id, статус, имя и размер файла, время, ошибка, сводка в JSON). После перезапуска незавершённые задачи помечаются как FAILED.

## 5. Алгоритм по шагам

### 5.1. Чтение и проекция
Файл разбирается потоково, объект за объектом, координаты сразу переводятся в UTM 37N — все длины и расстояния дальше в метрах. Битые объекты (нет `id`, нет `diameter`, пустая геометрия, неизвестный тип) не останавливают расчёт, а попадают в диагностику.

Файл читается **в два прохода**:
1. Точки подключения, сеть, камеры. По ним строится **область поиска** — круги вокруг зданий радиусом `1,5 × d + 200 м`, где d — расстояние от здания до ближайшей существующей трубы.
2. Только ограничения, которые касаются области поиска, расширенной на 650 м. Дальше ни одно ребро графа, ни отрезок до места врезки дотянуться не могут, так что эти объекты на результат не влияют. Сеть и камеры за этой границей тоже отбрасываются.

Зачем: файл в 3 ГБ — это фактически город, держать его целиком в памяти и строить граф вокруг каждого здания нельзя.

### 5.2. Группы зданий и расчётный диаметр
Два здания попадают в одну группу, если расстояние между ними меньше `1,5 × (d1 + d2) + 100 м`. Иначе общая труба заведомо не короче двух отдельных, и объединять их бессмысленно.

Отступы трассы от препятствий зависят от диаметра, а он известен только после построения сети. Поэтому трасса строится для **расчётного диаметра** — по суммарному расходу самой «тяжёлой» группы. Это с запасом: реальная труба не толще. На конкурсном наборе это ДУ 400.

### 5.3. Модель ограничений (`Env`)
- **Запрещённые объекты** (oks, park, social_area, prohibited_site, water, railway, неизвестные типы) — непроходимы. Расстояние считается от оси трубы: отступ + ½ ширины пары труб из таблицы 1.
- **Пересекаемые** (road, tram_tracks, gas_pipeline, power_cable, существующая heat_network) — можно пересечь спецпроходом. Спецпроход — один прямой отрезок: ±2 м от точки пересечения для линейных объектов или +3 м за границей полигона для дорог и трамвая. Для дорог и трамвая угол пересечения не меньше 45°. Вне спецпрохода действует горизонтальный отступ. Если спецпроходы накладываются, берётся наибольший Kспец (не суммируется).

Главная операция — `Env.eval(отрезок)`: проверить прямой отрезок трассы по всем правилам и вернуть его длину, «взвешенную» длину с Kспец и положение спецпроходов. Чтобы это было быстро, все отрезки препятствий лежат в пространственной сетке (`SegGrid`).

### 5.4. Граф видимости (`VisGraph`)
Вершины ставятся у выпуклых углов препятствий, со смещением наружу на величину отступа. Скругление отступа вокруг угла описывается ломаной, хорды которой не заходят в запретную зону. Контуры предварительно упрощаются (Дуглас–Пекер, 0,5 м), и смещение увеличивается на этот допуск. Вершины ставятся только внутри области поиска.

Рёбра — прямые отрезки не длиннее 700 м, прошедшие проверку `Env.eval`. Кандидаты в соседи берутся из соседних ячеек сетки, рёбра проверяются параллельно. На конкурсном наборе около 2,8 тыс. вершин и 88 тыс. рёбер, граф строится за ~1,5 с.

### 5.5. Подход к зданию
От точки подключения берётся ближайшая граница её полигона. Точка входа E ставится на продолжении этого направления, сразу за зоной отступа. Финальный прямой участок E → точка освобождён от отступа к собственному зданию (так разрешает ТЗ).

Иногда ближайшая граница выходит во внутренний двор или узкий проём, откуда нет пути к сети (на конкурсном наборе это здания 2, 3, 5 и 10). Тогда пробуются следующие по близости границы, и это явно пишется в проверках варианта. Это допущение — см. раздел 10.

### 5.6. Построение сети — жадный алгоритм (эвристика Прима для дерева Штейнера)
Сеть строится по одному зданию за шаг. На каждом шаге для каждого ещё не подключённого здания запускается поиск Дейкстры от его точки входа E по графу видимости. Вес ребра — его вклад в итоговый показатель:

```
w = 0,7 × L × цена_метра(ДУ) × Kспец / 25 млн + 0,3 × L / 100
```

Поворот круче 90° запрещён прямо в поиске. Целей две:

- **Врезка в существующую сеть.** Кандидаты — ближайшие точки на существующих трубах и существующие камеры. Если в пределах 10 м от точки врезки есть камера со свободным примыканием — врезка только в неё (5 млн ₽). Иначе новая камера на трубе, её цена — по наибольшему диаметру, включая существующую трубу.
- **Ответвление от уже построенной новой сети.** В точке ответвления ставится новая камера (3/5/8/12 млн ₽) или используется уже имеющаяся камера ветвления, если у неё меньше 4 примыканий. К цене добавляется удорожание общего участка: по нему пойдёт больше воды, и труба может стать толще — вплоть до места врезки.

Подключается здание с наименьшим приростом S. Проложенные участки становятся препятствием для следующих, поэтому новые трубы не пересекаются.

Ускорение: после каждого шага пересчитываются только те здания, до области поиска которых дотянулось изменение сети. Поиск Дейкстры с найденной ценой c не выходит за радиус c / (минимальная цена метра), поэтому результат такой же, как при полном пересчёте, но намного быстрее на больших наборах.

### 5.7. Локальное улучшение
Жадный алгоритм зависит от порядка подключения: первые здания задают магистраль, остальные к ней пристраиваются. Поэтому после жадного шага запускается улучшение порядка:

- здание переносится на другую позицию в порядке подключения, и сеть перестраивается заново в этом порядке;
- перенос принимается, если S уменьшился;
- переносы перебираются по кругу, пока полный круг не даст улучшения (локальный минимум) или пока не исчерпан лимит в 2000 перестроений на группу (время — только страховка, 60 с на вариант);
- улучшение идёт по каждой группе зданий отдельно — перестановки между независимыми группами ничего не меняют;
- итог сравнивается с жадным решением, хуже жадного результат не становится;
- перестановка отклоняется, если она заставляет снимать ограничения стратегии чаще, чем жадное решение (иначе «раздельный» вариант 3 «размывался» бы в совместный).

Эффект на конкурсном наборе: вариант 1 — S 12,697 → 12,423, вариант 3 — 48,59 → 36,54. Итог улучшения пишется в проверки варианта.

### 5.8. Подбор диаметров
Расход участка — сумма `flow_tph` всех зданий ниже по сети. Диаметр сначала минимальный по пропускной способности. Затем для каждого пути «здание → место врезки» проверяется длина непрерывной серии участков одного диаметра; если она больше предельной — диаметр всей серии повышается до следующего. Невозрастание диаметра к месту врезки поддерживается итеративно, пока всё не сойдётся.

### 5.9. Выходная геометрия
Цепочки между значимыми узлами (здание, камера) превращаются в LineString, повороты — вершины линии. Спецпроходы выделяются в отдельные участки, на их границах ставятся технические узлы (`technical_node`). Стоимость участка: `L × цена_метра(ДУ) × Kспец` (Kгл = 1, режим с глубиной не реализован).

### 5.10. Самопроверка
Каждый отрезок заново проверяется уже с **фактическим** диаметром: отступы, пересечения, углы, предельная длина. Результаты — в `checks` сводки варианта. Отдельно для каждого диаметра выводится наибольшая серия участков против предела (`dn_length_check`) — это требуется показать на защите.

### 5.11. Если маршрут не найден
Если поиск Дейкстры исчерпал граф и не нашёл ни врезки, ни ответвления, здание не подключается: штраф `100 млн + 0,5 млн × расход`, id в `unconnected_oks_ids`, причина в `checks`. Остальная сеть сохраняется. Отказаться от подключения ради лучшего S алгоритм не может: если маршрут есть, он будет выбран.

## 6. Варианты и ранжирование

ТЗ разрешает до трёх содержательно разных вариантов, и за варианты есть отдельный критерий оценки. У нас они такие:

1. **Совместное подключение** — основной ответ: здания объединяются в общую сеть с ветвлениями.
2. **Совместное, но с другими точками врезки** — места врезки варианта 1 запрещены в радиусе 40 м. Ответ на вопрос «а если там врезаться нельзя?» (камера занята, эксплуатирующая организация против).
3. **Каждое здание отдельно** — эталон для сравнения, показывает, сколько экономит совместное подключение.

Если стратегия варианта не даёт подключить какое-то здание (например, все доступные точки врезки запрещены), для этого здания ограничение снимается — варианты 2 и 3 не порождают искусственных неподключений.

Если вариант совпал с уже найденным (те же места врезки и то же разбиение зданий по частям сети), он отбрасывается. Оставшиеся ранжируются по S.

## 7. Входные и выходные данные

### Вход
См. таблицу в разделе 1. Идентификаторы могут быть строками или числами. Геометрия ограничений — LineString, MultiLineString, Polygon, MultiPolygon (Point тоже принимается). Неизвестные `restriction_type` учитываются как запрет с отступом 1 м и попадают в диагностику.

### Выход
Один GeoJSON FeatureCollection в WGS 84, варианты различаются `variant_id` (`v1`, `v2`, `v3`):

| `object_type` | Обязательные поля (раздел 7.2 ТЗ) | Наши дополнительные поля |
|---|---|---|
| `heat_network` | `id`, `variant_id`, `start_node_id`, `end_node_id`, `flow_tph`, `diameter`, `length`, `laying_method` (`base`/`special`), `depth_start` = null, `depth_end` = null, `cost` | `k_special` |
| `heat_chamber` (новые) | `id`, `variant_id`, `diameter`, `cost` | `chamber_role`: `tie_in` — на существующей сети, `branch` — ветвление |
| `technical_node` | `id`, `variant_id` | — |
| `variant_summary` (geometry = null) | `rank`, `construction_cost`, `chamber_construction_cost`, `existing_chamber_tie_in_count`, `existing_chamber_tie_in_cost`, `unconnected_penalty`, `calculated_cost`, `new_network_length`, `score`, `unconnected_oks_ids` | `strategy`, `network_parts`, `checks`, `dn_length_check` |

`start_node_id` / `end_node_id` ссылаются на id входной точки ОКС, входной существующей камеры, новой камеры или технического узла — и совпадают с геометрическими концами линии. Дополнительные поля ТЗ разрешает, при проверке они игнорируются.

Сводка задачи (`GET /api/jobs/{id}/summary`) дополнительно содержит статистику расчёта (`stats`: размер графа, время этапов, число групп, расчётный ДУ) и диагностику входных данных (`warnings`).

## 8. Как мы проверяем правильность

- **Самопроверка в сервисе** — раздел 5.10, результат в `checks` каждого варианта.
- **Независимый валидатор** `tools/validate.py` на чистом Python без зависимостей. Он заново проверяет результат по правилам ТЗ, не используя код сервиса:
  - топология: ссылки `start_node_id`/`end_node_id` совпадают с концами линий, нет циклов, всё связано с существующей сетью, новые линии не пересекаются, ветвления только в камерах, у точки ОКС одно примыкание, у технического узла два;
  - камеры: не больше 4 примыканий (с учётом существующих труб), ДУ и цена камеры;
  - геометрия: повороты ≤ 90°, отступы до запрещённых объектов, пересечения пересекаемых объектов только внутри спецпрохода, спецпроход — один прямой отрезок;
  - расходы и ДУ: расход участка равен сумме расходов ниже по сети, не превышает пропускную способность, ДУ не уменьшается к месту врезки, предельная длина серий;
  - деньги: длина и стоимость каждого участка, итоги сводки, S, список неподключённых.

  Не проверяет (пока): что выбран именно минимальный допустимый ДУ и угол ≥ 45° на дорогах и трамвае — это проверяет только самопроверка сервиса. Все наши результаты проходят валидатор без замечаний.
- **Тест** `EngineTest`: прогон ядра на конкурсном наборе — все здания подключены, нет нарушений. Запускается при каждой сборке Maven.
- **Регрессия при изменениях алгоритма**: все оптимизации скорости делались так, чтобы результат на конкурсных наборах совпадал до четвёртого знака S. Каждый раз это проверялось.
- **Стресс-наборы** `tools/make_big.py`: конкурсный набор, размноженный сеткой K×K. С ключом `--city` здания остаются только в одной копии — получается «город», на котором результат обязан совпасть с конкурсным.

## 9. Большие файлы и производительность

Ограничений по времени расчёта в ТЗ нет. Реальный риск — не «долго», а «не досчитает»: не хватит памяти или расчёт затянется на часы.

Что сделано:
- двухпроходное чтение и область поиска (раздел 5.1);
- вершины графа только в области поиска, соседи и места врезки ищутся по пространственным индексам;
- жадный шаг пересчитывает только затронутые здания;
- локальное улучшение — по группам, время делится между группами пропорционально размеру.

Замеры:

| Набор | Время | Примечание |
|---|---|---|
| Конкурсный, 17 зданий | ~57 с локально, ~90 с в Docker | из них ~53 с — локальное улучшение |
| «Город» 106 МБ, 50 тыс. объектов | ~60 с, память `-Xmx1g` | 50 274 объекта отброшены как лежащие вне области, результат совпал с конкурсным до цифры |
| 4 удалённые копии конкурсного, 68 зданий | ~200 с | 4 группы, расчётный ДУ 400 (раньше ошибочно считался ДУ 600 по сумме всех зданий) |

Файл в 3 ГБ целиком не прогонялся; время чтения растёт линейно, по оценке это 1,5–2 минуты чтения.

## 10. Допущения и открытые вопросы к организаторам

Всё это стоит проговорить на защите или уточнить заранее:

1. **Подход к зданию не с ближайшей границы.** У зданий 2, 3, 5 и 10 ближайшая граница выходит во двор или узкий проём, откуда нет пути к сети. Мы подводим трубу от соседней границы и пишем об этом в проверках. Если так нельзя, эти 4 здания окажутся неподключёнными со штрафом больше 100 млн ₽ каждое.
2. **Отступ у газопровода и кабеля.** Отступ (2 м + габариты) больше длины спецучастка (±2 м), выполнить оба правила буквально нельзя. Возле самой точки пересечения отступ мы не проверяем.
3. **Несколько полигонов с одним id** считаем одним зданием.
4. **Реконструкция существующей сети.** Описание кейса (PDF, п. 2.5, 2.11, п. 6 демонстрации) требует считать, как новые подключения меняют расход в существующей сети, и какие участки надо реконструировать. Техническое приложение (п. 2.4) и разъяснения (вопросы 14, 16) говорят обратное: существующая сеть не реконструируется, и при расхождении действует приложение. Во входных данных нет ни текущего расхода, ни связи «следующий участок к источнику», ни расценок реконструкции. Мы следуем техническому приложению и реконструкцию не считаем.

## 11. Что не сделано и куда развивать

- **Режим с учётом глубины** (дополнительная задача, п. 10 демонстрации) не реализован: `depth_*` = null, Kгл = 1. Оценка: полдня работы. Маршрут в плане почти не изменится (Kгл = 1 до глубины 3 м, поэтому обходить газопровод, кабель и теплосеть выгоднее сверху), основная работа — продольный профиль с уклоном 0,1 и технические узлы в изломах. Показывать на наборе с пересечениями.
- **Оптимальность.** Результат — локальный минимум хорошей эвристики, не доказанный оптимум. Следующие шаги по качеству: перекладка магистрали после подключения новых зданий, перебор точек ветвления и мест врезки, многократный старт из разных порядков.
- **Отступы под фактический диаметр.** Сейчас трасса строится под расчётный (самый большой) диаметр группы; узкий проход, куда пролезла бы только малая труба, может быть не найден. На конкурсном наборе эффект маленький (разница — полуширина трубы, ~0,4 м).
- **Карта для больших файлов.** Интерфейс не показывает исходные данные для файлов больше 80 МБ (только результат). Можно отдавать на карту только окрестность расчёта.

## 14. Вопросы, которые нам могут задать на защите

**Почему на конкурсном наборе нет спецпроходов через дороги?**
В конкурсном файле нет ни одной дороги — только здания, вода и железная дорога. Улицы на карте — это подложка OpenStreetMap, в расчёт она не входит и по ТЗ не должна. Спецпроходы показываем на копии набора с добавленными дорогой, газопроводом и кабелем.

**Почему почти всегда новые камеры, а не существующие?**
Вся существующая сеть в наборе — ДУ 400–500. Новая камера на ней стоит 5 млн ₽, ровно как врезка в существующую камеру. При равной цене решает длина трубы: новую камеру можно поставить в любой точке трубы, куда удобнее подойти, а к существующей надо тянуть дальше (ближайшие в 17–70 м). Алгоритм сравнивает оба варианта на каждом шаге, правило 10 м соблюдается. На толстой сети (ДУ 600+, новая камера 8–12 млн ₽) он сам выберет существующие.

**Почему три варианта?**
См. раздел 6: основной, резервный на случай запрета мест врезки, и эталон «каждое здание отдельно», который показывает выгоду совместного подключения.

**Это оптимальное решение?**
Нет, и доказать оптимум для такой задачи нельзя (задача Штейнера с препятствиями). Это хорошая эвристика плюс локальное улучшение — результат не хуже жадного и в локальном минимуме. Направления улучшения — раздел 11.

**Где реконструкция существующей сети?**
Раздел 10, пункт 4.

**Сколько считается?**
Конкурсный набор — около минуты (из них ~53 с — улучшение). Ограничений по времени в ТЗ нет. Файлы целого города обрабатываются за счёт области поиска.

**Будет ли работать на других данных?**
Да: в коде нет ни координат, ни id конкурсного набора, все числа ТЗ — в одном справочнике. Это проверено на размноженных и «городских» наборах, где структура и масштаб другие.
