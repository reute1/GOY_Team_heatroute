# Сервис моделирования трасс подключения к тепловым сетям

Прототип решения кейса ДИТ Москвы («Лидеры цифровой трансформации 2026»). Сервис получает один GeoJSON с существующей тепловой сетью, камерами, точками подключения перспективных ОКС и пространственными ограничениями. По нему он автоматически строит до трёх вариантов новой сети и выгружает результат в GeoJSON по разделу 7 технического приложения.

**Документация для команды:**
- [docs/01_project_overview.md](docs/01_project_overview.md) — подробное описание проекта: задача, архитектура, алгоритм, проверки, допущения, карта кода, вопросы к защите;
- [docs/02_setup_guide.md](docs/02_setup_guide.md) — как развернуть у себя: Docker, разработка без Docker, ядро из командной строки, инструменты, решение проблем.

## Быстрый старт

```bash
docker-compose up -d --build          # docker-compose 1.29.2, Ubuntu Server 22
# UI с картой:        http://localhost:8080/
# Swagger UI:         http://localhost:8080/swagger-ui.html
```

API:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/jobs` (multipart `file`) | загрузить GeoJSON (до 3 ГБ) и запустить расчёт |
| GET | `/api/jobs/{id}` | статус задачи (QUEUED / RUNNING / DONE / FAILED) |
| GET | `/api/jobs/{id}/summary` | сводка по вариантам, проверки правил, диагностика данных |
| GET | `/api/jobs/{id}/result` | результат GeoJSON (WGS 84) |
| GET | `/api/jobs/{id}/input` | исходный файл (для карты) |
| GET | `/api/jobs` | последние задачи |

Ядро можно запустить без Spring и без БД:

```bash
mvn package -DskipTests
java -Xmx4g -cp target/classes ru.lct.heatroute.core.HeatRouteEngine data/dataset.geojson result.geojson
```

Проверка результата независимым валидатором (Python, без зависимостей):

```bash
python3 tools/validate.py data/dataset.geojson result.geojson
python3 tools/plot.py data/dataset.geojson result.geojson v1 v1.png   # картинка (нужен matplotlib)
python3 tools/make_big.py data/dataset.geojson 20 city.geojson 5000 --city   # «город» для проверки больших файлов
```

## Стек

Java 11, Spring Boot 2.6.3 (`spring-boot-starter-parent`), springdoc-openapi-ui 1.7.0, PostgreSQL (статусы задач и сводки), docker-compose. Файлы хранятся на диске, входной файл читается потоково.

Ядро расчёта (`ru.lct.heatroute.core`) написано на чистом JDK, без внешних библиотек. В нём свой потоковый GeoJSON-парсер, проекция WGS 84 → UTM 37N (ряды Крюгера) и вычислительная геометрия. Так расчёт детерминирован и полностью под нашим контролем.

## Алгоритм

1. **Чтение и проекция.** Объекты разбираются по одному, прямо из потока. Координаты переводятся в EPSG:32637, все длины и расстояния считаются в метрах. Некорректные объекты не останавливают расчёт: они попадают в диагностику (`warnings`).
   Файл читается в два прохода. Первый — точки подключения, сеть, камеры; по ним строится **область поиска** (`SearchArea`): круги вокруг точек радиусом `1,5·d + 200 м`, где d — расстояние от точки до существующей сети. Второй проход берёт только ограничения, касающиеся области, расширенной на 650 м (дальше ни ребро графа — не длиннее `max-edge`, — ни отрезок до места врезки — не длиннее `tie-search-radius`, — не дотягиваются); сеть и камеры дальше области тоже отбрасываются. Поэтому файл целого города (до 3 ГБ) не держится в памяти целиком: остаётся только окрестность подключаемых объектов. Проверено: «город» из 400 копий конкурсного набора (106 МБ, 50 тыс. объектов, точки только в одной копии) считается с `-Xmx1g`, 50 274 объекта отброшены, результат совпадает с расчётом по исходному набору до цифры.
2. **Модель ограничений** (`Env`). Точки группируются: две точки в одной группе, если расстояние между ними меньше `1,5·(d1 + d2) + 100 м` — иначе общий участок заведомо не короче двух отдельных подключений. Расчётный ДУ — по суммарному расходу самой «тяжёлой» группы (консервативно для неё и не завышен для независимых групп: на наборе из четырёх удалённых копий конкурсного он остаётся ДУ 400, а не ДУ 600 по сумме всех точек). Для расчётного ДУ действуют такие правила:
   - **Запрещённые объекты** (oks, park, social_area, prohibited_site, water, railway, а также неизвестные типы) обходятся. Требуемое расстояние считается от оси трубы: отступ + ½ ширины пары. Для oks отступ зависит от ДУ: 5/7/9 м.
   - **Пересекаемые объекты** (road, tram_tracks, gas_pipeline, power_cable, существующая heat_network без врезки) можно пересекать спецпроходом. Спецпроход — один прямой участок с запасом ±2 м от точки пересечения или +3 м за границами полигона. Для дорог и трамвайных путей угол пересечения ≥45°. Вне зоны пересечения выдерживается горизонтальный отступ. Коэффициенты Kспец не суммируются: на перекрытиях берётся максимальный.
3. **Граф видимости.** Вершины ставятся у выпуклых углов препятствий, со смещением на отступ. Дуги скругления описываются ломаной, хорды которой не заходят в зону отступа. Для узлов контуры упрощаются по Дугласу–Пекеру, и смещение увеличивается на допуск упрощения. Рёбра — прямые отрезки, прошедшие проверку `Env.eval`. Строятся параллельно.
4. **Подход к ОКС.** От точки подключения берётся ближайшая граница её полигона. Точка входа E ставится на продолжении этого направления, за зоной отступа. Финальный прямой участок E→точка освобождён от отступа к собственному ОКС. Бывает, что ближайшая граница выходит во внутренний двор или в узкий проём, откуда нет пути к сети. Тогда пробуются следующие границы, и это явно помечается в `checks` варианта (см. «Открытые вопросы»).
5. **Построение сети (эвристика Прима для дерева Штейнера).** На каждом шаге для каждой неподключённой точки запускается поиск Дейкстры от E. Вес ребра — вклад в итоговый показатель: `0,7·L·c(ДУ)·Kспец/25 млн + 0,3·L/100`. Поворот больше 90° запрещён прямо в поиске. Есть две цели:
   - **врезка в существующую сеть.** Кандидаты — ближайшие точки на участках сети и существующие камеры. Работает правило 10 м: если рядом есть камера со свободным примыканием, врезка идёт в неё за 5 млн. Иначе ставится новая камера на трубе, её стоимость определяется по наибольшему ДУ, включая ДУ существующей сети;
   - **ответвление от уже построенной новой сети.** Ставится новая камера (3/5/8/12 млн), либо используется существующая камера ветвления, если у неё меньше 4 примыканий. К стоимости добавляется удорожание общего участка из-за роста расхода и ДУ вверх до места присоединения.

   Подключается точка с минимальным приращением S. Новые участки становятся препятствием для следующих: пересечения новой сети вне узлов исключены.
5a. **Локальное улучшение порядка вставки.** Жадный порядок подключения берётся стартовым решением. Затем точки по очереди переносятся на другие позиции, и лес перестраивается в новом фиксированном порядке (по одному поиску на точку вместо полного жадного шага). Перенос принимается, если итоговый S уменьшился. Перебор идёт по кругу и останавливается, когда полный круг переносов не дал улучшения, или по пределу `improveEvals` (2000 перестроений; время — только страховка `improveMs`), поэтому результат детерминирован. Перестановка отклоняется, если она увеличивает число точек, подключённых со снятым ограничением стратегии (иначе «раздельный» вариант размывался бы в совместный). Итог записывается в `checks` варианта.
6. **Подбор ДУ.** Расход участка равен сумме `flow_tph` точек ниже по сети. ДУ сначала берётся минимальный по пропускной способности. Затем для каждого пути «точка → место присоединения» проверяется предельная длина серии участков одного ДУ. Если она превышена, ДУ всей серии повышается до следующего. Условие невозрастания ДУ к месту присоединения поддерживается итеративно.
7. **Выходная геометрия.** Цепочки между значимыми узлами (точка ОКС, камера) превращаются в LineString. Повороты остаются вершинами линии. Спецпроходы выделяются в отдельные участки, на их границах ставятся technical_node. Стоимость участка: `L·c(ДУ)·Kспец` (Kгл = 1 в 2D).
8. **Варианты.**
   - (1) совместное подключение;
   - (2) совместное подключение, где точки врезки варианта 1 запрещены (радиус 40 м);
   - (3) раздельное подключение каждой точки.

   Если вариант совпадает с уже найденным (те же места присоединения и то же разбиение точек), он отбрасывается. Варианты ранжируются по `S = 0,7·C/25 млн + 0,3·L/100`.
9. **Самопроверка.** После построения каждый отрезок заново проверяется уже с фактическим ДУ: отступы, повороты, предельная длина. Результаты записываются в `checks` сводки варианта.

## Если маршрут не найден

Если в допустимом пространстве поиска для точки нет пути, то есть Дейкстра исчерпала граф, она не подключается. Для неё начисляется штраф `100 млн + 0,5 млн·G`, её id попадает в `unconnected_oks_ids`, а причина — в `checks`. Уже построенная часть сети сохраняется. Отказаться от подключения ради лучшего S алгоритм не может: подключение выбирается всегда, если маршрут существует.

Если стратегия варианта (запрет точек врезки или раздельная схема) не даёт подключить точку, для этой точки ограничение снимается. Так варианты 2 и 3 не порождают искусственных неподключений.

## Выходные данные

Один GeoJSON FeatureCollection (WGS 84), варианты различаются `variant_id`:

- `heat_network`: `start_node_id`, `end_node_id`, `flow_tph`, `diameter`, `length`, `laying_method` (base/special), `depth_start`/`depth_end` = null, `cost`. Дополнительно `k_special`.
- `heat_chamber` (новые): `diameter`, `cost`. Дополнительно `chamber_role` (tie_in — на существующей сети, branch — ветвление).
- `technical_node`.
- `variant_summary`: все обязательные поля раздела 7.2. Дополнительно `strategy`, `network_parts`, `checks`.

## Границы применимости прототипа

- Трасса строится для консервативного расчётного ДУ (по суммарному расходу группы точек). Поэтому узкие проходы, куда прошла бы только малая труба, могут быть не найдены.
- Эвристика жадная (Прим) с локальным улучшением порядка вставки: результат — локальный минимум, не гарантированный оптимум. На конкурсном наборе улучшение снижает S варианта 1 с 12,697 до 12,423, варианта 3 — с 48,59 до 36,54; расчёт занимает около минуты. Следующий шаг — перебор мест врезки и переподключение отдельных точек к другим частям сети.
- Масштабирование. Вершины графа ставятся только в области поиска, соседи ищутся по пространственной сетке, места врезки — по индексу отрезков сети. Жадный шаг пересчитывает только точки, в чью область поиска попало изменение сети (результат тот же, что при полном пересчёте). Локальное улучшение идёт по группам точек отдельно, время делится между группами пропорционально их размеру. На конкурсном наборе: ~2,8 тыс. вершин, граф ~1,5 с, весь расчёт ~1 мин (из них ~55 с — локальное улучшение, предел `improveMs`). На очень больших наборах, где улучшение останавливается по пределу времени, результат зависит от скорости машины.
- Режим с учётом глубины (доп. задача) не реализован: `depth_* = null`, Kгл = 1.

## Открытые вопросы к организаторам

1. Ближайшая граница полигона ОКС может выходить во внутренний двор, откуда нет выхода к сети. Допустим ли подход от другой границы, или такая точка считается неподключаемой?
2. Отступ к газопроводу или кабелю (2 м + габариты) больше, чем длина спецучастка (±2 м). Мы считаем, что отступ не проверяется в окрестности пересечения, пока угол не слишком острый. Так ли это задумано?
3. Несколько полигонов с одним `id` ограничения мы трактуем как один ОКС: исключение отступа для финального участка распространяется на все его части.
4. Реконструкция существующей сети. Описание кейса (п. 2.5, 2.11, п. 6 демонстрации) требует распространять дополнительный расход от точек врезки к источнику и определять участки под реконструкцию. Техническое приложение (п. 2.4) и разъяснения (вопросы 14 и 16) говорят обратное: существующая сеть не реконструируется, её расход не определяется, при расхождении применяется техническое приложение. Во входных данных нет ни текущего расхода участков, ни связи «следующий объект к источнику», ни расценок реконструкции, поэтому расчёт реконструкции не выполняется. Мы следуем техническому приложению.
